# Публікація аналітики з MD-брифу

Бриф — контракт між дослідженням (Cowork) і сайтом. Формат описано в
`cowork/cyberplain-analytics-brief/references/brief-format.md` і шаблонах `vulnerability.md`, `attack.md`, `report.md` поруч —
прочитай формат і шаблон свого виду перед роботою. Правила полів, мови й ілюстрацій — розділ «Аналітика» в `CLAUDE.md`,
схеми — `src/content.config.ts` (`reports`, `vulnerabilities`, `attacks`, `enReports`, `enVulnerabilities`, `enAttacks`).
Зразки: `content/analytics/**` і `content/en/analytics/**`, схеми `src/assets/analytics/*.svg`.

**Дослідження вже зроблено.** Факти, техніки й рішення беремо з брифу як є. Не дописуй фактів, яких у брифі немає, і не
«покращуй» зміст; редагувати можна лише мову (помилки, стиль сайту) і форму (довжину, розбиття на абзаци). Якщо бриф
суперечить правилам сайту чи сам собі — спитай автора, а не виправляй мовчки.

## 1. Прийняти й перевірити бриф

1. Збережи бриф у scratchpad (не в репозиторій).
2. **Формат — скриптом:** `npm run brief:check -- <шлях>`. Перевіряє `id` (формат, зайнятість), дати, CVE, кожну техніку й
   підтехніку за `data/mitre/attack.json` і описами, етапи кроків, класи, фази, повтори класів, `джерело`/`редакція`,
   обов'язкові розділи, примітку до цифр, alt і підпис схеми, підозру на IP/хеші. Помилки — це вже питання до автора
   (чи до Cowork); не виправляй їх мовчки, крім очевидних друкарських.
3. **Зміст — двома рецензентами** (`model: "sonnet"`) за `review.md` поруч: **facts** (джерела, статуси, подача й межа
   деталізації) і **mapping** (техніки ATT&CK і класи рішень) перевіряють паралельно; раунд 2 — лише якщо є `blocker`/`major`
   на межі ділянок; ти виносиш вердикт за доказами. Нотатка чи малий бриф — один рецензент (`facts`).
   Пропускай рецензію, лише якщо автор прямо сказав «без рецензії» (тоді — тільки п. 2 і п. 4).
4. Прочитай «Питання до автора» брифу. Усе, від чого залежить зміст (питання брифу, помилки скрипта, вердикти «зміст» і
   «спір» рецензії), постав автору **одним** AskUserQuestion до публікації. Суто довідкове — перелічи в звіті.

## 2. Українська версія — `content/analytics/<розділ>/<id>.json`

Розділи: `vulnerability` → `vulnerabilities`, `attack` → `attacks`, `report` → `reports`. Порядок ключів — як у зразках
(дивись найсвіжіший запис того ж виду). Порожні необов'язкові поля не пишемо (`exploitedSince`, `dateNote`, `original`,
`fixed`, `note`, `url`, порожні `caveats`/`gaps`/`claims` можна опустити або лишити `[]` — як у зразку). 2 пробіли, UTF-8,
текст без HTML і Markdown (крім звичайних символів).

| Бриф | JSON |
|---|---|
| `# Заголовок` | `title` |
| `## Коротко` | `summary` |
| `## Простими словами` (вразливість) | `description[]` — абзац = елемент |
| `## Простими словами` (атака) / `## Про що звіт` | `body[]` |
| `## Уражені версії` | `affected[] {product, versions, fixed?, note?}` |
| `## Наслідки`, `## Що робити` | `impact[]`, `remediation[]` |
| `## Бюлетені` | `advisories[] {issuer, label, url?}` |
| `## Хронологія` | `timeline[] {date, text}` |
| `## Заяви й цифри` / `## Цифри зі звіту` | `claims[]` + `claimsNote` / `figures[]` — `{value, label}` |
| `## Хто атакував` + передмова `actor` | `actor {name, profile[]}`; `victim {name, sector, country}` |
| `### Крок N. Назва` (атака, `## Кроки`) | `steps[] {title, tactic, what, result, tools[], techniques[], solutions[], gaps[]}` |
| `### Крок N. Назва` (вразливість, `## Ланцюжок атаки`) | `chain[]` — ті самі поля + `observed` (`Статус: підтверджено` → `true`, `ймовірно` → `false`); у JSON — після `impact` |
| `### 01 · Назва` (звіт) | `findings[] {title, basis, text, risk, techniques[], solutions[]}` — `title` разом із «01 · »; «- Основа:» → `basis` (`дані звіту` → `data`, `рекомендація автора` → `recommendation`, `наш висновок` → `editorial`), «Що на кону:» → `risk` |
| `## Як отримано дані` (звіт) | `method[]` — пункт = елемент; у JSON після `body` |
| `## Питання до замовника` (звіт) | `questions[]`; у JSON після `gaps` |
| `## Висновки` (атака) | `lessons[]` |
| `## Прогалини`, `## Застереження` | `gaps[]`, `caveats[]` (`—` = порожній масив) |
| `## Джерела` | `sources[] {label, url?}` — `[текст](url)` → `label` + `url` |
| `## Ілюстрація` | `illustration {file, alt, caption}` — у всіх трьох видах (у звіті — після `summary`); «Вид» у JSON не йде, лише визначає, що малювати |
| передмова `related-vulnerabilities` | `vulnerabilities[]` (атака, звіт) |
| передмова `original` (звіт; атака — якщо є) | `original {title, publisher, pages?, url?}` |
| `## Питання до автора`, `## Перевірка фактів` | на сайт не йдуть |

Таблиці:
- **Техніки**: `редакція` без «Як у джерелі» → рядок `"T1190"`; `джерело` → `{ "id": "T1190", "editorial": false }`;
  є «Як у джерелі» → `{ "id": "T1690", "asInSource": "T1562.003", "editorial": false }` (`editorial: true` замість false,
  якщо зіставлення наше).
- **Рішення**: `{ "class": "vm", "why": "…" }` + `"editorial": true` для `редакція` (для `джерело` поле можна опустити або
  `false`, як у зразку); у загальній таблиці «Рішення» вразливості — ще `"phase"` одразу після `class` (у кроках `chain[]`
  фази немає — схема її не прийме).
- У кроках (атака й ланцюжок вразливості) «Що відбувається» → `what` (разом з реченням «Аналогія: …»), «Що отримує зловмисник» → `result`
  (на сторінці — блок «Що отримав зловмисник»), «Інструменти» (через `;`) → `tools[]`, «Прогалини:» кроку → `gaps[]` кроку.
- Порядок рішень з брифу зберігай — він за ефективністю.

## 3. Англійська версія — `content/en/analytics/<розділ>/<id>.json`

Обов'язкова. Лише текстові поля з дозволеного списку в `src/content.config.ts` (`enVulnerabilities` тощо); масиви тієї
самої довжини й порядку; елементи об'єктів — лише перекладені ключі (`solutions: [{ "why": "…" }]`, `steps[].solutions`, `chain[]` — `title`/`what`/`result`/`tools`/`solutions`/`gaps`,
`affected[]` — `product`/`versions`/`fixed`/`note`, якщо в них є кирилиця, інакше `{}`). `original`, `sources`,
`advisories`, ID, дати, класи, техніки не перекладаємо й не повторюємо. Перекладай природною англійською (як у зразках),
не дослівно; власні назви — латиницею як в оригіналі; українські назви (АТБ, ДТЕК Енерго) — транслітерацією, як у
наявних оверлеях (`ATB`, `DTEK Energo`). Після злиття не має лишитися кирилиці — `loadData('en')` зупинить збірку.

## 4. Ілюстрація — `src/assets/analytics/<file>.uk.svg` і `.en.svg`

Ілюстрація є в **кожній** статті. Вид — з брифу: **схема** (механіка вади, шлях атаки, темп, смуги цифр звіту, структура
документа — зразки: `atlassian-cve-2026-21589`, `tradertraitor-binance`, `picus-blue-report-2026`, `picus-post-mythos`) або
**образ** — проста образна ілюстрація головної думки, коли схема не має сенсу (метафора з аналогії статті: геометричні
форми, лінії й 3–6 коротких підписів, без людей-персонажів, логотипів і фото). Для однакової геометрії обох мов зручно
генерувати SVG невеликим скриптом у scratchpad (тексти uk/en — словником). Малюй у стилі наявних (відкрий 1–2 як зразок):
- `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 800 H">`, H ≈ 400–500; без `width`/`height`, `style`, шрифтів і
  кольорів у коді — **лише класи** з `src/components/Illustration.astro`: текст `tm` (основний), `ts` (другорядний),
  `k` (моно-підпис UPPERCASE), `ta`/`td` (атака/захист); блоки `b`, `b-out`, `b-att`, `b-def`, `b-dash`; лінії `lm`, `la`,
  `ld`, `lg`, `dash`; заливки стрілок `fm`, `fa`, `fd`, `fg`.
- Маркери стрілок — у `<defs>` з **унікальним префіксом** для цієї схеми (`<pfx>-mm`, `<pfx>-ma`), бо SVG інлайниться
  на сторінку й ID не мають збігатися з іншими схемами.
- Текст ≥ 11px (`font-size`), рамки `rx="4"`–`"6"`, сітка з кроком 8; текст не виходить за блоки — перевір на рендері
  через `getBBox()` кожного `<text>` проти його рамки (так ловляться підписи, що «впираються» в край).
- Дві мови — **однакова геометрія**, різняться лише тексти; англійський текст довший — перевір, що влазить.
- Зверни увагу: `alt` і `caption` — у JSON (`illustration`), не в SVG.

### Прев'ю для соцмереж

`npm run og:analytics -- <id>` → `public/og/analytics/<id>.uk.png` і `.en.png` (1200×630, заголовок і джерело зі статті).
Переглянь обидві картинки: заголовок має влазити в 3 рядки (інакше скрипт попередить).

## 5. Перевірка

1. `npm run build` — без помилок і без нових попереджень про цю статтю. Помилки `loadData()` вказують файл і поле.
2. Переглянь сторінки `/analytics/<розділ>/<id>/` і `/en/analytics/<розділ>/<id>/` (`npx astro preview` + Playwright,
   `chromium.launch()`), ширина **375px і 1440px**: схема читається й скролиться в рамці, нічого не налазить, таблиці
   й списки на місці. Скриншоти — лише для себе (deviceScaleFactor 1).
3. Перевір, що стаття з'явилась у списку розділу й на `/analytics/`, а пов'язана вразливість (якщо є) показує її у
   зворотному зв'язку.
4. `npm run cowork:skill -- --no-zip` — оновити `cowork/cyberplain-analytics-brief/references/existing.md` новою статтею.

## 6. Коміт

Один коміт: JSON, оверлей, обидві SVG, обидва PNG прев'ю, оновлений `existing.md`. Повідомлення в стилі історії:
`Аналітика: <вид> <коротко>` (напр. «Аналітика: вразливість CVE-2026-21589 в Atlassian Data Center (читання файлів без
пароля)»). Гілка й пуш — за правилами `CLAUDE.md` («Як працювати») і поточної сесії. Лічильники в `README.md` аналітика не
змінює; якщо бриф вимагав нових класів чи продуктів — це окреме завдання, спитай автора.

Звіт автору — коротко: адреси обох сторінок, що редакційне, що змінено в тексті порівняно з брифом і чому, які питання
з брифу лишились відкритими.
