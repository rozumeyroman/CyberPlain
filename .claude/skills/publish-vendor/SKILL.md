# Публікація вендора з MD-брифу

Формат брифу — `cowork/cyberplain-vendor-brief/references/brief-format.md`, стиль текстів — `style.md` поруч. Модель
продукту й сторінка — `CLAUDE.md` («Сторінка продукту», «Портфель рішень»), схема — `src/content.config.ts` (`products`,
`enProducts`). Зразки: будь-який вендор у `content/solutions/products/` (напр. `fortinet-fortigate-*`).

**Дослідження вже зроблено.** Класи, редакції й факти беремо з брифу. Мову й форму можна правити, зміст — лише через автора.

## 1. Прийняти й перевірити

1. Збережи бриф у scratchpad.
2. **Формат — скриптом:** `npm run vendor:check -- <шлях>` (передмова, ID і префікс, новий / наявний вендор, класи,
   таблиця доказів на кожен клас, лінійки й редакції, обов'язкові поля). Помилки — питання до автора.
3. **Зміст — двома рецензентами** (`model: "sonnet"`) за протоколом `.claude/skills/publish-analytics/review.md`, ролі
   «для вендорів»: **packages** (редакції за таблицею пакетів + тексти очима продавця) і **classes** (класифікація за
   правилами портфеля). Раунд 2 — лише якщо є `blocker`/`major` на межі ділянок; бриф на 1–2 продукти — один рецензент
   (`packages`).
   Пропускай рецензію лише за прямим «без рецензії».
4. **Пропозиції змін класів** (новий клас, зміна `defenses[]` / `d3fend[]`) і всі вердикти «зміст» / «спір» — автору
   одним AskUserQuestion до публікації. Новий клас = окреме рішення автора з `risk`, `simple`, `d3fend[]` і `defenses[]`.

## 2. Дані — `content/solutions/products/<id>.json`

| Бриф | JSON |
|---|---|
| `### <id> · <назва>` | ім'я файлу = `id`; `name` = назва |
| передмова `vendor` | `vendor` (однаково в усіх продуктах) |
| `- Лінійка / Редакція / Порядок` | `line`, `edition`, `order` (для «—» поля не пишемо) |
| `- Класи` | `classes[]` у тому ж порядку |
| `Коротко:` | `summary` |
| `Що дає замовнику:` | `value[]` |
| `Детально:` | `simple` |
| `Чого немає:` / `Як класифікували:` | `notIncluded[]` / `classification[]` (`—` = поле не пишемо) |
| `- URL` | `url` |
| таблиця доказів, «Питання до автора», «Перевірка фактів» | на сайт не йдуть |

Порядок ключів: `name, vendor, line, edition, order, classes, summary, value, simple, notIncluded, classification, url`.
Режим `update`: міняй лише те, що змінилось; продукт, якого вендор більше не продає, — питання автору (видаляти чи ні).

## 3. Англійська — `content/en/solutions/products/<id>.json`

`summary`, `value[]`, `simple`, `notIncluded[]`, `classification[]` — природною англійською, масиви тієї ж довжини.
Назви продуктів і функцій — як у вендора. Назви класів в англійських текстах — англійськими (`EDR`, `web filtering`).

## 4. Пам'ять сайту — `CLAUDE.md` і `README.md`

- `CLAUDE.md` → «Портфель рішень»: перелік вендорів у першому абзаці, рядки таблиці «Продукт | Класи» і абзац із
  «Рішення щодо класифікації» брифу (у стилі сусідніх абзаців). Новий клас — і згадка в правилах.
- `README.md` → «Чесно про обмеження»: кількість продуктів, вендорів, класів і перелік вендорів — звір із `/vendors/`.
- `npm run cowork:skill -- --no-zip` — оновлює довідники обох скілів Cowork (`existing-products.md`, `classes.md`,
  `portfolio-rules.md`, `portfolio.md`); нагадай автору перезавантажити zip.

## 5. Перевірка

1. `npm run build` без помилок і без нових попереджень `EN:`.
2. Сторінки нових продуктів (uk і `/en/`) на 375 і 1440 px: таблиця редакцій скролиться в рамці, ризики й покриття етапів
   на місці, сторінка не ширша за екран (перевір `scrollWidth` для всіх нових сторінок).
3. `/vendors/` показує вендора з правильною кількістю продуктів; лічильники головної збігаються з `README.md`.

## 6. Коміт

Один коміт: продукти, оверлеї, `CLAUDE.md`, `README.md`, довідники Cowork. Повідомлення: `Рішення: <вендор> — <N> продуктів
(<лінійки коротко>)`. Гілка й пуш — за `CLAUDE.md` і правилами сесії. Звіт автору: що додано, які класи спірні й як
вирішено, що лишилось відкритим, і таблиця рецензії.
