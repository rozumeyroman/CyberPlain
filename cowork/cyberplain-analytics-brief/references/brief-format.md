# Формат MD-брифу

Бриф — один файл `<id>.md` у UTF-8. Він складається з **передмови** (YAML між `---`), **розділів для сайту** (заголовки
`##` / `###` із назвами нижче — **дослівно**, бо Claude Code шукає їх за назвою) і **службових розділів** (на сайт не
йдуть). Порядок розділів — як у шаблоні виду статті. Розділ, для якого немає даних, лишай із текстом `—` (не видаляй),
щоб було видно, що його не забули.

## Передмова (спільні поля)

```yaml
---
type: vulnerability            # vulnerability | attack | report
id: atlassian-cve-2026-21589   # латиниця малими, цифри й дефіси; стане адресою /analytics/<розділ>/<id>/
date: 2026-11-05               # YYYY, YYYY-MM або YYYY-MM-DD (див. «Дати»)
dateNote: ""                   # пояснення, коли дата неточна чи подія розтягнута; інакше ""
related-vulnerabilities: []    # лише attack і report: ID уже опублікованих вразливостей з existing.md
---
```

Поля для конкретного виду — у його шаблоні. Значення з двокрапками, лапками чи `#` бери в лапки `"…"`.

**ID.** Коротко й упізнавано: вразливість — `<вендор чи продукт>-cve-<рік>-<номер>` або назва вади, якщо вона є
(`php2shell`); атака — `<угруповання>-<жертва>` (`tradertraitor-binance`); звіт — `<видавець>-<назва>-<рік>`
(`picus-blue-report-2026`). ID не повинен збігатися з жодним в `existing.md`.

**Дати.** `date` — дата, якою стаття стоїть у списку: вразливість — дата публікації бюлетеня виробника (або CVE);
атака — дата самої атаки (для кампанії — дата хвилі чи попередження CERT); звіт — дата документа. Знаєш лише місяць —
`YYYY-MM`; дати в документі немає — найкраща оцінка + `dateNote` («Дата в документі не вказана; написано до липня 2026»).

## Розділи для сайту (спільні)

### `# Заголовок`
Перший рядок після передмови: `# <заголовок>`. До ~80 символів. Атака: «<Угруповання> проти <жертви>: <суть>»;
вразливість: CVE чи назва вади + продукт; звіт: назва звіту українською + суть через двокрапку.

### `## Коротко`
2–3 речення, до ~420 символів: що сталося, чому це важливо, що буде нижче. Без ID технік і жаргону.

### Таблиця технік ATT&CK
Використовується в розділі «Техніки ATT&CK» (вразливість) і всередині кожного кроку (атака) чи висновку (звіт):

```markdown
| ID | Хто зіставив | Як у джерелі | Чому |
|---|---|---|---|
| T1190 | джерело | | бюлетень прямо називає експлуатацію вебзастосунку |
| T1005 | редакція | | читання конкретного файлу на сервері |
| T1690 | джерело | T1562.003 | у джерелі старий ID; у v20 — Impair Command History Logging |
```

- **ID** — техніка чи підтехніка з `attack-v20.md`. Сторінка на сайті завжди батьківська, але підтехніку видно.
- **Хто зіставив**: `джерело` — джерело саме назвало цю техніку (ID чи однозначна назва MITRE); `редакція` — наш висновок
  (на сайті позначається «*»). Сумніваєшся — `редакція`.
- **Як у джерелі** — лише коли ID у джерелі інший, ніж у v20; інакше порожньо.
- **Чому** — службове пояснення для перевірки (на сайт не йде), коротко.

### Таблиця рішень
```markdown
| Клас | Фаза | Хто | Чому (why) |
|---|---|---|---|
| vm | find | джерело | Перевірки Rapid7 InsightVM знаходять вразливі Jira без пароля. Окремий звіт за CVE допомагає стежити за строками. |
| mfa | protect | редакція | MFA для адміністраторів не дасть увійти з одним лише викраденим паролем. |
```

- **Клас** — ID з першої колонки `portfolio.md`. Один клас — один раз у списку (у вразливості — один раз на фазу).
- **Фаза** — лише у вразливості: `find` (знайти вразливі системи), `protect` (прикрити до чи замість оновлення),
  `verify` (перевірити, що захист працює), `detect` (виявити сліди, якщо вже атакували). В атаці й звіті колонку
  лишай порожньою.
- **Хто** — `джерело`, якщо джерело згадує цей клас чи конкретний продукт класу як захід; інакше `редакція`.
- **Чому (why)** — іде на сайт і є **обґрунтуванням** для замовника. До двох речень про **цей** крок чи висновок:
  (1) механізм — що саме клас бачить чи блокує в цьому кроці, спираючись на його сліди («бачить, що процес Java чи Tomcat
  запускає оболонку, і ізолює сервер»); (2) умова чи обмеження, за яких спрацює («лише в режимі Prevent», «працює лише з
  розшифровкою HTTPS», «якщо агент стоїть і на macOS»). Не «підвищує захищеність» і не загальний опис класу.
  Продукт називай, лише якщо про нього каже джерело, і без реклами. Не використовуй символ `|` у тексті клітинки.
- **Порядок — за ефективністю на цьому кроці**: першим — клас, що розриває ланцюг найраніше й найнадійніше (запобігає),
  далі — що виявляє, наприкінці — що зменшує наслідки чи допомагає розслідувати. Зазвичай 3–6 класів на крок атаки,
  8–16 на вразливість, 2–5 на висновок звіту. Краще три точні класи, ніж шість «про всяк випадок».
- Не стався до таблиці як до переліку всього, що «теж корисно»: клас без зв'язку зі слідами чи механікою кроку — зайвий.

### `## Прогалини`
Список: що допомогло б, але класу в портфелі немає (процес, архітектура, налаштування самого продукту, мікросегментація,
навчання конкретній процедурі). Кожен пункт — одне-два речення: що зробити і чому це не продукт. Немає — `—`.
(В атаці прогалини пишуться всередині кроків, окремого загального розділу немає.)

### `## Застереження`
Список: що в статті не підтверджено, чого не розкрито, де джерела розходяться, які техніки ми свідомо **не** ставимо й
чому, станом на яку дату дані про захист від вендорів. Немає — `—`.

### `## Джерела`
Список від найважливішого: `- [Видавець: назва (дата)](https://…)`. Немає URL у самому джерелі (PDF від автора,
закритий звіт) — без посилання: `- Picus Security: Blue Report 2026 (PDF, 2026)`. URL — лише перевірені, які ти відкрив.

### `## Ілюстрація` (вразливість і атака)
Опис нашої SVG-схеми механіки (Claude Code намалює її в стилі сайту, ширина 800 px):

```markdown
- Файл: atlassian-cve-2026-21589        # зазвичай = id
- Що показує: що саме може прочитати нападник і де стоять захисні рубежі
- Блоки: «НАПАДНИК · без пароля» (атака) → «WAF · IPS · блокує запит» (захист) → рамка «СЕРВЕР ATLASSIAN»: всередині
  «web root — ДОСЯЖНО» (атака) і пунктиром «home-каталог — зазвичай недосяжно»; нижній ряд — «вхід → нові акаунти → вивантаження» (атака, пунктир = ймовірно)
- Стрілки й підписи: «запит», «origin lock» (захист), «обхід напряму без origin lock» (атака)
- Alt: Схема: нападник без пароля надсилає запит … (повний опис для читача з екранним диктором, 2–4 речення)
- Підпис: Що саме може прочитати нападник і де стоять захисні рубежі. Наша схема за описами Atlassian, watchTowr і Rapid7; кроки в нижньому ряду — ймовірний сценарій, а не підтверджені спостереження.
```

Правила схеми: кольори лише за змістом — **атака** (фіолетовий) і **захист** (зелений), решта нейтральна; пунктир —
умовне чи ймовірне. 6–14 блоків, короткі підписи (до ~30 символів у рядку), без логотипів. Для атаки — шлях від входу
до мети з 2–3 найдешевшими «точками розриву» або темп атаки на шкалі часу. Підпис **завжди** каже, за якими джерелами
схема і що в ній наше чи умовне. Схема не потрібна — напиши `—` і чому.

## Службові розділи (на сайт не йдуть)

### `## Питання до автора`
Нумерований список: що не вдалося перевірити, де потрібне рішення автора (класифікація продукту, чи ставити клас, як
назвати угруповання українською), що варто уточнити у вендора. Немає — `—`.

### `## Перевірка фактів`
Таблиця для кожного ключового факту статті (цифри, дати, версії, CVSS, суми, атрибуція, цитати):

```markdown
| Факт у статті | Джерело (з розділу «Джерела») | Примітка |
|---|---|---|
| CVSS 4.0 — 9.3 | Atlassian, бюлетень | NVD ще не оцінив |
| перші спроби через ~2 год після деталей | Rapid7 ETR | 15 спроб з 3 IP за honeypot Previdian |
```

## Самоперевірка перед здачею

- [ ] Передмова повна; `id` унікальний і в правильному форматі; дати у форматі `YYYY[-MM[-DD]]`.
- [ ] Усі заголовки розділів — дослівно як у шаблоні; порожні розділи мають `—`.
- [ ] Кожен ID техніки є в `attack-v20.md`; кожен клас — у `portfolio.md`; класи не повторюються в одному списку.
- [ ] `джерело` / `редакція` чесні: `джерело` лише там, де джерело справді це каже.
- [ ] Кожна цифра й дата є в «Перевірці фактів»; заяви угруповання мають примітку; дані вендорів названо даними вендора.
- [ ] Посилання лише ті, що відкривались; IoC не переносимо (посилання на джерело).
- [ ] Кожен крок атаки має «Що отримує зловмисник»; механіка й наслідки описані детально, але без коду, пейлоадів, команд
      і запитів із параметрами (тест — `style.md` → «Деталізація атаки»).
- [ ] Рішення кожного кроку впорядковані за ефективністю; кожне `why` називає механізм і умову спрацювання.
- [ ] Тон і мова — за `style.md`; є аналогія для нефахівця.
